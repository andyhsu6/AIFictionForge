# Internationalization (i18n) Guide

How internationalization works in AIFictionForge and how to contribute
translations or new user-facing strings. The UI ships two locales:
**`zh` (Simplified Chinese, the product default and source language)** and
**`en` (English)**. Issue/PR language policy: [CONTRIBUTING.md](../CONTRIBUTING.md).

## Architecture overview

- Init: `frontend/src/i18n/index.ts` — react-i18next with `fallbackLng: 'zh'`,
  `supportedLngs: ['zh', 'en']`, `defaultNS: 'common'`, browser language
  detection via `localStorage` → `navigator` → `<html>`. Variants such as
  `zh-CN` / `en-US` are normalized to `zh` / `en` by `normalizeLanguage()`
  in `frontend/src/i18n/normalize.ts`.
- Resources: `frontend/src/i18n/resources.ts` aggregates every locale JSON from
  `frontend/src/locales/{zh,en}/<namespace>.json` (37 namespaces, one per page
  or feature area, plus `common` and `errors`).
- Because `fallbackLng` is `zh`, a key missing only in `en` does **not** warn —
  it silently renders the Chinese string. That failure mode is what the CI
  gates and the render smoke test below exist to catch.

### Tooling (configured in `frontend/i18next.config.ts`)

| Script | What it does |
| --- | --- |
| `npm run i18n:extract:ci` | Scans `src/**/*.{ts,tsx}` for `t()` calls and re-generates `src/locales/{{language}}/<ns>.json`; `--ci` mode fails if anything changed. |
| `npm run i18n:types:ci` | Re-generates `src/types/i18next.d.ts` from the `zh` JSON files (type-safe keys); `--ci` mode fails on diff. |
| `node scripts/check-locale-parity.mjs` | zh/en must have the same namespace files, the same base keys, no empty values, and complete plural groups per locale convention. |

CI gate: `.github/workflows/i18n-check.yml` runs `i18n:extract:ci`,
`i18n:types:ci`, `check-locale-parity.mjs` and `npm test` on every PR and push
to `main`. All four must be green; a locale edit that leaves generated
artifacts stale fails the zero-diff checks.

## Adding a UI string

1. In the component, call `const { t } = useTranslation('<namespace>')` and use
   `t('myGroup.myKey')` (`common` is the default namespace for shared strings).
2. Run `cd frontend && npm run i18n:extract` — the key is seeded into
   `src/locales/zh/<ns>.json` (zh is the primary language) and merged into `en`.
3. Fill in the English value in `src/locales/en/<ns>.json`. **Never leave it
   empty** — empty values fail the parity check. Placeholders use i18next
   syntax: `t('preview.chaptersTitle', { count })` ↔ `"{{count}} chapters"`.
4. For count-dependent text, author an en plural group (`_one` + `_other`); zh
   uses a single form whose value must be identical across suffixed members.
5. Re-run `npm run i18n:types` so the key becomes type-safe, then commit the
   generated JSON/type artifacts together with the component change; CI
   verifies both stay in sync. Runtime guarantees (no raw CJK leaking into the
   `en` DOM, no missing keys, synced language switch, antd/dayjs locale) are
   enforced by the `frontend/src/i18n-integrity/` vitest suites.

## Backend error codes → localized messages

User-visible backend text is internationalized through a structured error
envelope, not by translating server strings on the fly. Every error response
body is:

```json
{ "detail": "原始中文文案", "code": "auth.login_failed", "params": {}, "raw": "..." }
```

- `detail` keeps the original Chinese text for backward compatibility.
- `code` + `params` are the fields the frontend translates; `params` feeds
  i18next placeholders (`{{param}}`).
- `raw` is optional (task 14a "dual channel"): the original diagnostic text for
  debug surfaces only. It is omitted unless set; production 500s never leak
  exception text into it.

### Registry

- Raise errors as `raise ApiError(code="auth.login_failed")` — see
  `backend/app/core/errors.py`. `ERROR_REGISTRY` maps each code to a default
  Chinese `detail` and HTTP status; `detail`/`status` can be overridden,
  `params`/`raw` are optional.
- Legacy `HTTPException`s are auto-classified by reverse lookup on
  `(status_code, detail)`; unregistered ones get the `http_error` fallback code
  with the original text moved to `raw`.
- The 422 validation handler generates `errors.validation.<pydantic_type>`
  codes; truly unknown exceptions become `internal.error` (500).

### Frontend mapping

`frontend/src/services/errorMapper.ts` (`mapErrorPayload`) resolves display
text, in order:

1. Known code with an `errors.json` entry (registry codes nest under their
   group object, e.g. `auth.login_failed`) → localized template with `params`
   interpolated.
2. Code without a locale entry (including `http_error` and `dynamic_detail`
   runtime-composed sites) → localized **generic** message; the backend
   `detail` never leaks to the UI.
3. Payload with **no** code at all (legacy task rows / legacy SSE events) →
   `detail` verbatim — the only remaining raw-text escape.
4. Otherwise a per-HTTP-status fallback key, then `errors:unknown`.

`getErrorDiagnostic()` exposes `raw || detail` strictly for debug/detail views.
SSE error/progress events and background-task rows follow the same policy via
`mapSSEError` / `mapSSEProgressMessage` / `mapTaskStatusMessage`.

Adding a new error code: add it to `ERROR_REGISTRY` in
`backend/app/core/errors.py`, raise it with `ApiError(code=...)`, and add the
matching key to `frontend/src/locales/{zh,en}/errors.json`. An unknown code
never breaks the UI — it degrades to the generic message.

## AI-generated content language (`content_language`)

The language of AI-generated *content* (chapters, outlines, characters, …) is
independent of the UI locale and resolved by
`backend/app/services/language_resolver.py` (`resolve_generation_language`):
**per-generation request override > user preferences.content_language >
user preferences.language (UI language) > `"zh"`**.

- Any level that is `None`, `"auto"` or invalid falls through to the next one;
  the resolved value is always `"zh"` or `"en"`.
- The instruction (e.g. "Please respond in English.") is appended to the
  rendered prompt by `append_language_instruction()` — editable prompt
  templates need no language variable, and legacy templates keep working.
- Per-generation overrides ride on generation requests (wizard, chapters,
  book-import tasks) and background task rows.

## Testing

- Backend: `cd backend && .venv/bin/python -m pytest tests/ -v` — includes the
  error-code registry/envelope/handler and language-resolver chain suites.
- Frontend: `cd frontend && npm test` — node:test units
  (`src/i18n/normalize.test.mjs`, `src/services/errorMapper.test.mjs`) plus
  vitest, including `src/i18n-integrity/` (registry↔`errors.json` parity,
  error contract, language sync, full-route CJK/missing-key smoke).
- Locale hygiene: `node scripts/check-locale-parity.mjs` from `frontend/`.
